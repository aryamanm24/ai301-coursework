# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| repo-not-archived | The `archived:` field on the repo line under Repo facts (live: the archived banner on the repo front page). | The repo is not archived (`archived: no`). An archived repo is read-only and fails. | required |
| recent-commits | The dates in `last 5 default-branch commits` under Repo facts, measured against the bundle's `captured` date (live: today). | At least one of those five commits is dated within 90 days of the captured date. Recency is about whether humans still ship to the default branch, not star count. If the commit list is missing, grade unclear. | required |
| bounded-scope | Issue title, body, labels, and the comment thread. Grade the size of the work asked for, not the polish of the write-up. | Pass if the issue is one bounded change a newcomer can implement without inventing a product decision: one bug, one named behavior, one function or file, or one docs change. A terse body, missing repro steps, or a good-first-issue label do not fail this check when the opener is a maintainer or the behavior to change is named. Fail if any of: (1) the issue is an umbrella, tracking issue, or megaissue, or it invites codebase-wide incremental work without naming the specific unit to change; (2) the thread is an unresolved design debate and no OWNER/MEMBER/COLLABORATOR has settled what to build; (3) it is a usage/support question rather than a code or docs change; (4) it is a feature request whose desired behavior is still unspecified, so the contributor would have to make a product call. Closed unmerged PRs are a difficulty signal only when the design is also still unsettled. | required |
| unclaimed | Repo facts `this issue: assignees:` and `linked PRs:` plus claim language in the Comments section. | Pass only if all three hold: assignees is `none`; no linked PR is `open`; and the thread has no active claim within 90 days of the captured date ("I'll take this", "working on this", "I created the pull request", `@bot claim`). Closed or merged linked PRs do not fail. Claims older than 90 days do not fail, including when a maintainer later invited other takers. A bot inactivity nudge does not clear an assignee or an open linked PR. | required |
| ai-policy-allows | The `contribution policy` line under Repo facts (live: CONTRIBUTING.md, linked contributor docs, AI_POLICY.md / AI_USAGE_POLICY.md). | Pass if the repo is silent on AI, has no CONTRIBUTING.md, or allows AI-assisted work with conditions (disclose, understand, test, human-review, "assistive AI allowed", "fully AI-generated PRs not accepted" while assistive use is allowed, "discouraged without human review"). Fail only on an outright ban of AI-generated code or documentation (for example "we do not accept AI-generated"). Conditions are not bans. | required |
| recent-release | `latest release` under Repo facts, measured against the captured date (live: today). | Latest release is dated within 180 days of capture. "none published" fails this check. Preferred only: a repo can be alive on commits alone. | preferred |

## Verdict rule

Accept if and only if every required check is pass. Preferred checks never change the verdict; they only rank issues that already accepted. Treat unclear on a required check as fail: a first issue you cannot verify is not a first issue to take.
