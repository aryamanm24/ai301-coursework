# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-follows-repro | The plan's stated cause (the Diagnosis, Cause, or opening paragraph that names what is wrong) read against the Repro evidence section only. Thread comments are not repro evidence. | Pass if that cause is consistent with the repro's failing run and its controls: it explains the behavior the artifacts show, and no control, comparison, or earlier-step artifact in the Repro evidence contradicts it. Fail if any of these is true: (1) a control shows the blamed component already behaving correctly, or shows the symptom on a path that does not involve that component; (2) the symptom disappears when a subsystem the plan calls unrelated is turned off, or remains when the blamed component is not running; (3) an earlier artifact shows the data already damaged or discarded before the step the plan will change, so that later step cannot restore what the artifact shows is gone. A short cause that names the site the repro isolates passes. Quoting a thread comment whose theory the controls contradict is a fail. If the Repro evidence section is absent, grade unclear. | required |
| scope-bounded | The changes the plan says it will make in this change (in-scope list, proposed changes, approach steps), read against the one behavior in the issue body. Lines marked not in scope, deferred, separately, later, will not, or follow-up are not part of this change. | Pass if the work that will actually land is one bounded change at the site the cause names, plus a regression test of the repro. Naming a larger idea only to defer it is a pass. Noting other sites in the PR without editing them is a pass. Fail if this change will also land any of the following, even when the core fix is right and even if the author offers to split PRs later: a rewrite of a subsystem beyond that site, a new user-facing option or prop or setting, a dependency migration, a new settings or UI panel, a retry framework, a cross-runtime or cross-construct abstraction, a new CI matrix, a test-harness migration, or a while-in-the-area fix of a different issue. | required |
| stranger-can-start | The plan's files or areas together with the edit it will make (approach or change steps). The test plan is not this evidence. | Pass if a stranger could open a named file, module, function, or code site (a path, a function, or a site the repro already isolates) and make a stated edit there: add, remove, or change a named behavior. A note that the exact function name will be confirmed while implementing does not fail when the module and the edit are already named. An unknown stated as unknown does not fail when the edit site is still specified. Fail if no file, module, function, or isolated site is named, or if the edit itself is deferred: "somewhere", "whichever is easier", "not sure which layer", "investigate and fix once the cause is clear", or "optimize whatever profiling finds". | required |
| test-observable | The plan's test plan only, read against the symptom in the Repro evidence. | Pass if the test names the repro, a fixture taken from it, or a command, and a checkable outcome: an exit code, specific printed text, an assertion, the symptom absent (no panic, color flips, class removed, valid file type), or a comparison with a stated reference result. Fail if there is no test of the reproduced behavior, or if the outcome that decides success is subjective ("feel fast", "feel broken", "look much better", "looks better"). | required |
| thread-direction | Thread highlights whose role is OWNER, MEMBER, or COLLABORATOR, read against the plan's chosen approach and the candidate plan comment. | A direction is a comment from one of those roles that names a source file or function as the culprit, posts a patched binary or commit and asks for it to be tested, or states the fix to make. Pass if the thread has no direction. Pass if the planned change touches the named file or function, implements the stated fix, or the plan comment explicitly says it is following that direction (including choosing one of several options the comment listed and naming which). Fail if a direction exists and the plan comment never mentions it and the planned change does not touch the named file or the requested test (a docs-only workaround that leaves the named culprit untouched is a fail). Questions, version notes, and "contributors welcome" are not directions. | required |
| ai-disclosure | The Repo facts `contribution policy` line, plus the candidate plan comment. The plan body does not count. | Pass if the policy does not require disclosing AI usage in comments. "Understand the work", "assistive AI allowed", "human in the loop", "comments must be written by humans", "state the tool in the pull request", and "low-quality AI content is closed" are not a comment-disclosure requirement. Fail only when the policy requires disclosure in comments or issues (for example "must be disclosed" or "all AI usage … must be disclosed") and the plan comment does not name the AI tool or that AI assistance was used. These packages are AI-assisted work. | required |

## Verdict rule

Accept if and only if every required check is pass. Preferred checks never change the verdict. Treat unclear on a required check as fail: a plan you cannot verify from the package is not ready to build from. There is no third verdict.
