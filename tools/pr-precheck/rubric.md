# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-match | The Diff, read against the Plan context scope (in scope, not in scope, deferred, deviation note) and against Description sentences that say what the diff contains or does not contain. | Pass if every change in the diff is the change the plan names. A piece the plan marks deferred, not in scope, or a known limit is not a deliverable of this PR, and leaving it out passes when the description says so too. Fail if the plan names a deliverable and the diff does not contain it, unless the description states that omission. Fail if the diff adds behavior the plan did not ask for or marked out of scope (a new flag or config option, a rename pass, a rewrite of a function the plan did not name, unrelated help-text edits) while the description claims the PR matches the plan ("exactly", "exactly as planned", "implements the posted plan", "no other behavior changes", "no functional changes outside"). Fail if the description claims a deliverable the diff does not contain, such as a docs page the diff never edits. | required |
| repro-shown | The Test evidence section, plus a fenced block in the Description when the test evidence says the output is there. Compare it with the failing command or scenario in the Plan context. | Pass if a fenced block shows that failing path, with a before and an after or an after next to the result the plan said to expect, and the fence contains what was run and what it printed. Fail if the only proof is prose with no fence ("tested locally", "colors work now", "verified working", "tests pass", "cargo test passes", "a full day"). Fail if the fenced run is a control the repro says already succeeds (a single-file case, a GET, the path that never breaks) and the plan's failing command is not shown. | required |
| no-debris | Added lines in the Diff. | Pass if the added lines are the planned edit and its test. Fail if an added line is a debug leftover: a commented-out print, a line containing `DBG` or `DEBUG`, a commented-out first attempt, an unused function, or `dead_code`. Fail if a hunk only regroups imports the plan did not mention, or repeats removed lines with the same text. An edit that changes a value and rewraps that same line is not debris. An `eprintln` the plan asked for as a log line is not debris. | required |
| standards | The Repo facts pull-requests line and contribution-policy line, read against the Description. When a required checklist names a whatsnew or changelog file, also look at the Diff. | Pass unless one of these is true. Fail if the pull-requests line says the template is a required checklist and the description has no issue link (`Closes` or `Fixes` with a number) or no checklist, or the named whatsnew entry is missing from both the description and the diff. Fail if the policy says AI usage must be disclosed ("must be disclosed" or "all AI usage") and the description does not say that AI assistance was used or name the tool. "Written by humans", "understand the work", and a pull-request-only note are not a disclosure fail. These packages are AI-assisted work. | required |

## Verdict rule

Accept if and only if every required check is pass. Preferred checks never change the verdict. Treat unclear on a required check as fail. There is no third verdict.
